## What Went Well

### 1. Functional extension delivered end-to-end — real product value

The extension detects LinkedIn profiles, shows a badge (red = new, green = already in CRM), and opens a pre-filled form for add/update. This changes the daily workflow of a salesperson and is a significant value-add for BattleCRM.

### 2. Clean dual-auth architecture

Session guard (`web`) for the web app and Access Tokens guard (`extension`) for the extension were properly isolated from day one. No confusion between the two mechanisms in the rest of the codebase.

### 3. Zero regressions across 6 stories

245 → 265 functional backend tests, all passing throughout. Stable design signal.

### 4. Adversarial code review very effective (especially Story 7.2)

8 non-trivial corrections caught before merge:
- Race condition on `prospect.save()` with unique LinkedIn URL constraint → try/catch → 409
- Test "no active funnel stage → 422"
- `.url()` validation on `linkedin_url` (rejects non-URL strings with 422)
- Dead UUID guard removed (route-level constraint already handles it)
- All `ExtensionProspectData` fields asserted in check test
- PATCH non-UUID id format → 404 test

### 5. WXT tooling mastered despite initial friction

Despite setup challenges (see Challenges section), WXT proved to be the right choice: Vite-based, React module, cross-browser, ~43% smaller bundle than Plasmo.

### 6. `chrome.storage.session` keyed by URL — elegant MV3 solution

The service worker terminates after 30s of inactivity in MV3. Caching check results and form state in `chrome.storage.session` keyed by normalized LinkedIn URL solves this robustly without complex persistence logic.

## Challenges

### 1. WXT + Tailwind v4 tooling conflict

`@tailwindcss/vite` conflicts with WXT 0.20.20 (WXT uses Vite 7.3.1, `@tailwindcss/vite` 4.1.18 expects Vite 8+). Solution: `@tailwindcss/postcss` via `postcss.config.mjs`. Not obvious upfront — cost real setup time.

**Lesson:** When integrating a new toolchain, validate version compatibility with the full dependency tree before starting implementation.

### 2. `tsconfig.json` standalone (WXT/Vite 7 incompatibility)

Cannot use `"extends": ".wxt/tsconfig.json"` — Vite 7's esbuild fails to resolve this path during build. Solution: standalone `tsconfig.json` that includes `.wxt/wxt.d.ts` directly. Counter-intuitive and underdocumented.

### 3. `auth:make-tokens-migration` Ace command doesn't exist

Expected a standard Adonis CLI command — had to read the source of `access_tokens_guard/main.js` to reconstruct the migration schema manually. SHA-256 hash (not bcrypt as assumed). Documented in completion notes.

### 4. Extension E2E test coverage is near-zero in CI

Almost all extension UI ACs are manual verifications (`[ ]` checkboxes in story tasks). The Playwright extension scaffold exists (`tests/e2e-extension/`) but concrete tests are still skipped. A regression in the popup flow won't be caught by CI.

**Decision:** Extension tests will be addressed in a dedicated epic after Epic 6. Not blocking, but a known risk.

### 5. Architecture pivot mid-epic: panel → popup (2026-04-21)

The initial plan used `chrome.windows.create` for a floating panel (separate window). This was abandoned in favor of a single `popup/` entrypoint with form state persisted in `chrome.storage.session`. This architectural decision emerged during Stories 7.3/7.4, not in planning — Story 7.6 spec still referenced "floating window" language and required adjustments.

**Lesson:** For extension-specific features with no prior team experience, consider a spike/proof-of-concept story before committing architecture in the epic plan.

### 6. LinkedIn DOM selectors are fragile by nature

LinkedIn DOM changes periodically. The company extraction is wrapped in try/catch, multiple fallback selectors are used, and `''` (not a wrong value) is always returned on failure. This is correct behaviour per the AC, but requires ongoing monitoring.

## Key Insights

1. **Honor previous retro commitments first** — 8/8 Epic 5B items done before Epic 7 started. This is why the epic started smoothly. Retrospective discipline compounds over time.

2. **MV3 service worker lifecycle is a real constraint** — the 30s termination kills any in-memory state. `chrome.storage.session` is the correct solution. Document this pattern; it will apply to future extension features.

3. **Specs age** — Story 6.2 (next epic) still references `interaction.status`, a field dropped during Epic 7 (migration `0010_drop_status_from_interactions.ts`). A spec written months ago can reference architecture that no longer exists. Audit ACs before coding.

4. **Code review adversarial process catches non-trivial issues** — not just style, but race conditions, missing test cases, dead code. Worth the investment on every story.

5. **Single `name` field beats split Prénom/Nom** — simpler, handles non-Western names, matches the backend model. The field split added complexity with no real benefit.
