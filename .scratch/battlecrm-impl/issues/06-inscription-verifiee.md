# 06: Inscription vérifiée

**What to build:** une personne s'inscrit avec un e-mail et un mot de passe, reçoit un lien de vérification dans sa langue, clique dessus et arrive connectée sur « Aujourd'hui » vide. Une adresse déjà prise donne la même réponse à l'écran et un e-mail « Tu as déjà un compte ». Inscriptions fermées par défaut. Sources : spec UX §5.9 ; spec stack §7, §8 ; ADR 0010 ; ST-10 à ST-14, ST-37 (la création des Étapes types arrive au ticket 14), ST-40.

**Blocked by:** 02, 03

**Status:** resolved

- [x] Better Auth (≥ 1.7.7, adaptateur Drizzle, tables générées et migrées, hors RLS avec des `GRANT` limités) derrière une liste blanche de chemins dans Hono ; tout le reste répond 404 ; test d'instantané des routes de Better Auth
- [x] Inscription maison : chaque tentative est une ligne `pending_signup` (e-mail, empreinte du mot de passe, langue, fuseau détecté par le navigateur, empreinte du jeton) ; compte créé seulement au clic (lien 24 h, usage unique), avec le mot de passe de cette tentative, qui ouvre une session (cookie `__Secure-`, HttpOnly, SameSite=Lax, 90 j glissants)
- [x] À la création du compte : langue et fuseau écrits par le module `settings` (fuseau en valeur en vigueur `(user_id, effective_from, value)`) ; point d'extension « compte créé » pour les tranches suivantes
- [x] Mots de passe 15 à 128 caractères, aucune autre règle ; HIBP en k-anonymat, injoignable = refus (faux HIBP en test) ; message de la spec UX §10
- [x] `SIGNUPS_OPEN` (fermé par défaut), `GET /api/config` → `{ signupsOpen }` ; porte fermée : le lien « Créer un compte » disparaît, la page affiche « Les inscriptions sont fermées pour le moment. » ; une tentative commencée reste vérifiable
- [x] Module `email` : interface `EmailTransport`, Nodemailer sur Gmail, gabarits `(params, locale) → { subject, text, html }` avec échappement testé ; `verify_email` et `account_exists` dans la langue de la tentative ; envoi après le commit sans `await`, échec journalisé (adresse masquée) et alerté ; faux transport en test
- [x] Écran « Vérifie ta boîte mail » identique adresse libre ou prise ; « Renvoyer le lien » réémet un jeton pour la même tentative, avec délai
- [x] Sélecteur de langue discret sur tous les écrans d'authentification, langue préremplie depuis le navigateur
- [x] Purge des `pending_signup` non vérifiées à 7 jours, en tâche du module `jobs` si le ticket 05 est fait, sinon notée pour lui (ST-21)
- [x] Garde de la SPA : sans session, toute page de l'app renvoie à l'authentification ; fabrique de test `makeUser()` (Utilisateur vérifié et son cookie)

## Comments

**2026-10-11, implémentation (agent).**

- **Better Auth 1.7.7** (version exacte, adaptateur Drizzle de `better-auth/adapters/drizzle`) dans `apps/api/src/auth/better-auth.ts` : sessions opaques 90 j, `updateAge` 1 j, `cookieCache` coupé, ids générés par la base, cookie `__Secure-battlecrm.session_token` (HttpOnly, SameSite=Lax), télémétrie coupée. Les quatre tables (`user`, `session`, `account`, `verification`) sont écrites à la main dans `auth/tables.ts` plutôt que générées par la CLI : un test les compare à ce qu'attend la version installée (`getAuthTables`). Migrations `0001` (tables) et `0002` (`GRANT` limités : ni `DELETE` sur `user` et `account` ; RLS forcée sur les tables de `settings`).
- **Liste blanche vide pour l'instant** (`ALLOWED_NATIVE_ROUTES`) : aucun endpoint natif n'est joignable, tous répondent 404 (test généré depuis l'instantané des 32 routes). La SPA demande la session à une route maison, `GET /api/session` (`{ email }` ou 401), parce que `/get-session` renvoie le jeton de session au JavaScript. Le ticket 07 ouvrira `POST /sign-in/email` et `POST /sign-out`.
- **Écart à la spec stack §7 et ST-14, à trancher** : les plugins `twoFactor` et `haveIBeenPwned` ne sont pas installés. L'inscription maison n'est pas un endpoint de Better Auth, le plugin ne la verrait pas : le contrôle HIBP est le nôtre (`auth/hibp.ts`, k-anonymat, `Add-Padding`, délai de 5 s, injoignable = refus en 503), derrière l'interface `Hibp` injectée dans `createApp`. Le ticket 09 peut le réutiliser pour le changement et la réinitialisation, ou brancher le plugin ; `twoFactor` arrive au ticket 11.
- **Routes maison** : `POST /api/signup` (202 `{ attemptId }` ; 403 `signups_closed`, 400 `password_compromised`, 503 `password_check_unavailable`), `POST /api/signup/resend` (204, ou 429 `{ retryAfterSeconds }`), `POST /api/signup/verify` (200 `{ email }` et le cookie, ou 400 `invalid_link`), `GET /api/config`. `createApp` renvoie désormais `{ app, jobs }`.
- **Adresse déjà prise** : elle reçoit aussi sa ligne `pending_signup` (jamais cliquable, purgée à 7 jours), ce qui rend les deux cas identiques, réponse et durée comprises. Au clic, `insert … on conflict do nothing` sur l'e-mail : une tentative commencée avant que l'adresse ait un compte meurt.
- **Clic** : une seule transaction `withUser` (id tiré de `uuidv7()` avant) crée `user` et `account` avec l'empreinte de cette tentative, efface les autres tentatives de l'adresse et appelle les gestionnaires « compte créé ». La session est ouverte après le commit par l'adaptateur interne de Better Auth, le cookie signé par Hono (même format, prouvé par un test). Si l'ouverture échoue, le compte existe sans session : sans gravité une fois la connexion livrée (07).
- **Le jeton voyage dans le fragment** (`/verify-email#<jeton>`) : il n'atteint aucun journal de serveur. C'est la SPA qui le poste, dans le `loader` de la route (une fois par visite) : un robot de messagerie qui précharge le lien ne le consomme pas. Seule son empreinte SHA-256 est en base.
- **Délai de 60 s entre deux envois**, par tentative (« Renvoyer le lien ») et par adresse (une nouvelle inscription sur la même adresse dans la minute répond pareil et n'envoie rien). Un clic sur un lien expiré laisse la tentative en place, « Renvoyer le lien » la ranime. La limitation par IP reste au ticket 07.
- **Point d'extension « compte créé »** : `OnAccountCreated = (tx, { userId, locale, timeZone, now })`, liste composée dans `createApp` (`onAccountCreated: [initializeSettings]`). **Le ticket 14 y ajoute les Étapes types.**
- **Module `settings`** : `user_settings (user_id, locale)` et `effective_time_zone (user_id, effective_from, value)`, sous RLS. Le premier fuseau vaut à partir du jour local de la création. Un fuseau inconnu de l'API devient `UTC` plutôt que de bloquer l'inscription.
- **Module `email`** : `EmailTransport`, `gmailTransport`, `createEmailSender` → `sendEmail(to, template, params, locale)` (la langue en plus de la signature de la spec : celle de la tentative). Gabarits `verify_email` et `account_exists`, textes Paraglide `email_*`, échappement par le tagged template `html`. Les messages sont embarqués dans le bundle de l'API (`noExternal`), et son image installe `@battlecrm/api...` pour les compiler : trouvé par l'e2e, l'API ne démarrait pas dans l'image.
- **Purge** : tâche `purge unverified sign-ups` du module `auth`, inscrite par `main.ts` (`jobs` de `createApp`).
- **`POST /api/client-errors` exige la session** (`auth.requireUser`) : une erreur sur un écran d'authentification n'est donc plus remontée.
- **SPA** : routes `/sign-in` (coquille : le titre et « Créer un compte », le formulaire arrive au ticket 07), `/sign-up`, `/verify-email`. Le routeur reçoit `{ api, queryClient }` en contexte ; une route sans chemin `app` garde toute l'app. **Seul un 401 renvoie à la connexion** : si l'API ne répond pas, la coque s'affiche quand même (lecture hors ligne, ADR 0004 ; l'API refuse de toute façon). Sélecteur de langue sans rechargement (`changeLocale`, `useLocale`), la saisie est conservée. Ajout hors spec : « Ce n'est pas la bonne adresse ? » (ticket UX 16).
- **Tests** : `makeUser(harness)` (`apps/api/test/factories/user.ts`) passe par la vraie inscription et le vrai clic ; `testApp()` expose `emails()`, `hibp`, `jobs` ; `testBetterAuth()` pour interroger Better Auth depuis un test. Côté web, `fakeApi()` et `renderApp(path, api)` (Utilisateur connecté par défaut). L'e2e de fumée attend désormais l'écran de connexion.
- **Configuration, obligatoire au démarrage** : `BETTER_AUTH_SECRET` (32 caractères au moins), `SMTP_USER`, `SMTP_PASSWORD` ; `SIGNUPS_OPEN` et `EMAIL_FROM_NAME` facultatifs. **À faire sur le VPS avant de livrer** : les ajouter à `api.env` (`ops/prod/api.env.example`, `docs/ops/install.md`), sinon l'API refuse de démarrer et `deploy.sh` revient au tag précédent. En dev : `SMTP_USER` et `SMTP_PASSWORD` dans `apps/api/.env.development.local` (ignoré par git).
- **Spec stack §2 amendée** : un `tables.ts` peut importer le `tables.ts` d'un autre module pour une clé étrangère (ici `settings` → `user`), avec un commentaire de désactivation du lint.
- **Laissé aux tickets suivants** : l'e-mail `account_exists` pointe vers `/sign-in` (coquille jusqu'au 07) et `/forgot-password` (ticket 09), sans conséquence tant que `SIGNUPS_OPEN=false` ; les schémas de requête et les constantes partagées (15 à 128, 60 s) restent répétés entre l'API et la SPA faute de `@battlecrm/contract` importable par l'API (note du ticket 02) ; aucun parcours e2e d'inscription (il faudrait un faux SMTP et un faux HIBP dans `compose.e2e.yml`).
- **Vérifié à la main** sur les images de `compose.e2e.yml` : `GET /api/config`, 401 sans session, 404 sur `/api/auth/sign-up/email`, refus d'un mot de passe fuité par le vrai HIBP, tentative écrite en base, échec SMTP journalisé avec l'adresse masquée.
