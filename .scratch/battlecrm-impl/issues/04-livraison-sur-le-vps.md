# 04: Livraison sur le VPS

**What to build:** poser un tag `v*` sur `main` livre l'API et la SPA sur `app.battlecrm.romainsire.com` : CI rejouée, images poussées, migrations passées, santé attendue, retour automatique au tag précédent en cas d'échec. Les sauvegardes quotidiennes tournent et la restauration est documentée et essayée. La V1 est retirée. Sources : spec stack §10, §12 ; ADR 0013.

**Blocked by:** 02, 03

**Status:** ready-for-human

L'écriture des fichiers (images, compose, scripts, workflows, docs) est à la portée d'un agent ; l'installation sur le VPS, les secrets, le DNS, la bascule V1 et l'essai de restauration demandent Romain. Les notes d'infrastructure de `.private/` ne sont jamais copiées dans un fichier suivi.

- [x] Images `api` (node:24-alpine, multi-étapes, `pnpm deploy --prod`, points d'entrée `main` et `migrate`) et `web` (nginx non privilégié, en-têtes de la spec stack §10.2 ; l'hôte de la landing répond sans contenu tant que la landing n'existe pas), `linux/amd64`, publiques sur GHCR
- [x] Compose de prod (`web`, `api`, `postgres`, `migrate`) : exclus de Watchtower, limites mémoire, journaux en rotation, Postgres sur le seul réseau interne, `postgresql.conf` versionné, un `.env.example` par service
- [x] `deploy.sh <tag>` : tag validé, `migrate` (échec = arrêt), `up -d`, attente de `/api/health`, retour automatique au `deployed_tag` ; dépose `ops/backup.sh`
- [x] Workflow `release` : refuse un tag hors de `main`, rejoue la CI, pousse `1.2.3` et `sha-<court>`, lance `deploy.sh` en SSH (commande forcée, utilisateur `battlecrm-deploy`), crée la GitHub Release ; retour arrière par `workflow_dispatch`
- [x] Vérifié : `pnpm version` crée bien le tag préfixé `v` dans le workspace (spec stack §15)
- [ ] `ops/backup.sh` : `pg_dump -Fc` à 3 h, rétention 30 jours, ping d'un moniteur push distinct ; `docs/ops/restore.md` écrit et restauration essayée une fois à la main (**essayée sur une pile de test ; reste à le faire sur le VPS**, case suivante)
- [x] Harnais e2e : compose e2e contre les images construites, Playwright Firefox et Chromium, un test de fumée sur `/api/health` et la coque, job CI parallèle
- [ ] Sur le VPS (Romain) : V1 supprimée sans dump, ancienne clé retirée, DNS `app.battlecrm.romainsire.com`, secrets écrits en 600, moniteurs uptime-kuma créés, première release livrée

## Comments

**2026-10-09, implémentation (agent).** Partie agent terminée ; reste la case « Sur le VPS (Romain) », guidée par `docs/ops/install.md`.

- **Images** : `apps/api/Dockerfile` et `apps/web/Dockerfile`, construits depuis la racine (`.dockerignore` en liste blanche : ni `.private/` ni `.scratch/` dans le contexte). Couche `pnpm fetch` sur le seul lockfile, puis `pnpm deploy --prod` (l'API déclare `files: ["dist", "drizzle"]`). Bases épinglées : `node:24.17.0-alpine` (comme `.node-version`), `nginxinc/nginx-unprivileged:1.30.5-alpine`. **Écart à la spec stack §10.4, reporté dans la spec** : `APP_VERSION` est inscrit dans l'image (`--build-arg VERSION`), pour qu'un retour arrière annonce la bonne version sans toucher `api.env` ; `APP_ORIGIN` est déduit de `APP_HOST` par le compose.
- **nginx** (`ops/web/`) : gabarit rendu au démarrage avec `APP_HOST`/`SITE_HOST` ; SPA avec repli sur `index.html` (`no-cache`), `/assets/` immuable et 404 si absent ; l'hôte de la landing répond 204. En-têtes de la spec §10.2 dans un extrait inclus par chaque `location` (un `add_header` de location efface ceux du serveur). **CSP** : `style-src 'self'` plus deux empreintes sha256, celles des deux `<style>` fixes qu'injecte React Aria (`usePress`, `usePreventScroll`) ; sans elles, le test de fumée échoue (vérifié en retirant l'une d'elles). Une montée de React Aria qui les change sera arrêtée par l'e2e de sa PR Renovate.
- **Compose de prod** (`ops/prod/docker-compose.prod.yml`) : tous les conteneurs exclus de Watchtower, `mem_limit` = `memswap_limit` (sans swap), journaux en rotation, Postgres sur le réseau `internal` (`internal: true`) seul, `web` et `api` en lecture seule, `cap_drop: ALL`, `postgresql.conf` versionné (`ops/postgres/`, sans paramètres dans les journaux). Postgres porte un nom fixe, `battlecrm-postgres`, pour `backup.sh` et la restauration. **Trouvé à l'essai** : `migrate` était tué par l'OOM à 256 Mio, car V8 laisse la mémoire à ramasser du chargement de drizzle (~170 Mo) grandir faute de plafond ; il reçoit `--max-old-space-size=128`.
- **Le compose voyage dans l'image** : le compose, `postgresql.conf`, `initdb/` et `backup.sh` sont copiés dans `/ops` de l'image de l'API ; `deploy.sh` les en extrait pour le tag livré (y compris lors d'un retour arrière), sans dépendre de GitHub. `deploy.sh` lui-même s'installe à la main et ne se remplace jamais.
- **`deploy.sh`** : tag validé, verrou `flock`, pull, `run --rm migrate`, `up --wait` (healthcheck de l'API sur `/api/health`), puis `deployed_tag` ; tout échec revient au tag précédent. Essayé dans un Docker-in-Docker isolé : livraison, montée, migration en échec (l'API en place n'est pas redémarrée, puis retour au tag précédent, sans effet), santé en échec (retour au tag précédent), tags invalides refusés.
- **Workflow `release`** : vérifie le format, l'égalité avec la version du `package.json` et l'appartenance à `main`, rappelle `ci.yml`, pousse les images (`docker buildx`, sans action tierce), SSH, GitHub Release. `workflow_dispatch` ne fait que relivrer un tag. Groupe de concurrence `deploy` : celui de `ci.yml` aurait bloqué (un workflow appelé prend le nom de l'appelant). `ci.yml` ne tourne plus sur les tags (`branches: ['**']`). **Écart, reporté dans la spec** : secrets `DEPLOY_KNOWN_HOSTS` (clé d'hôte épinglée plutôt que `ssh-keyscan` à chaque fois) et `DEPLOY_PORT` facultatif.
- **`pnpm version`** (spec §15) : vérifié dans un clone jetable, `pnpm version minor` crée le commit `0.1.0` et le tag **annoté** `v0.1.0` (donc poussé par `git push --follow-tags`). Le `package.json` racine reçoit `"version": "0.0.0"`.
- **Sauvegardes** : `backup.sh` (dump via `docker exec`, contrôlé par `pg_restore --list`, écrit en `.partial` puis renommé, 30 jours, ping de `BACKUP_PUSH_URL` dans `backup.env`). `docs/ops/restore.md` suivi pas à pas sur la pile de test : vérification dans une base à part, puis remplacement de la base ; propriétaire et RLS conservés.
- **e2e** : workspace `e2e` (ajouté au tableau §2 de la spec), `compose.e2e.yml` construit les images, avec un Traefik en fournisseur de fichier qui reprend les deux routeurs de la prod. 4 tests × Chromium et Firefox : santé, coque sans violation CSP ni erreur, lien profond et asset absent, landing 204. `pnpm e2e:up`, `pnpm e2e`, `pnpm e2e:down` ; job `e2e` en parallèle dans `ci.yml`.
- **Laissé aux tickets suivants** : `api.env.example` ne liste que ce que `config.ts` lit aujourd'hui ; chaque ticket qui ajoute une variable (auth, SMTP, `SIGNUPS_OPEN`, `UPTIME_KUMA_PUSH_URL`) complète l'exemple et `install.md`. La version de la SPA (pour `X-App-Version`, ticket 43) n'est pas encore passée à l'image `web`.
- **Revue** : `compose.e2e.yml` recopie une partie du compose de prod (dérive possible, acceptée pour garder deux fichiers lisibles).
