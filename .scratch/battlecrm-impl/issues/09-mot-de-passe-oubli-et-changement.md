# 09: Mot de passe oublié et changement

**What to build:** l'Utilisateur réinitialise un mot de passe oublié par un lien d'une heure, ou change son mot de passe depuis Réglages › Compte en redonnant l'actuel ; dans les deux cas, ses autres appareils sont déconnectés et un e-mail part. Sources : spec UX §5.9 ; spec stack §7 ; ADR 0010 ; ST-12, ST-16, ST-20.

**Blocked by:** 07

**Status:** resolved

- [x] Mot de passe oublié : message toujours neutre (« Si un compte existe pour cette adresse, un lien vient de partir. »), e-mail `password_reset_link`, jeton à usage unique de 1 h
- [x] Fin de réinitialisation maison (le `/reset-password` natif reste hors liste blanche) : nouveau mot de passe (HIBP), révocation de toutes les sessions, levée du blocage de `login_attempt`, connexion de l'appareil ; point d'insertion prévu pour le code 2FA (ticket 11)
- [x] Réauthentification : le mot de passe accompagne chaque requête sensible, vérifié côté serveur, sans fenêtre ; mécanisme réutilisable par les tickets 10 et 11
- [x] Changer le mot de passe : réauthentification, HIBP, révocation des autres sessions, e-mail `password_changed`

## Comments

**2026-10-12, implémentation (agent).**

- **Routes** : `POST /api/password-reset` (`{ email }` → 204 toujours ; 400 `invalid`), `POST /api/password-reset/complete` (`{ token, password }` → 200 `{ email }` et le cookie de session ; 400 `invalid_link` ou `password_compromised` ; 503 `password_check_unavailable`), `POST /api/account/password` (session exigée, `{ password, newPassword }` → 204 ; 403 `wrong_password` ; 429 `too_many_attempts` ; 400 `password_compromised` ; 503 `password_check_unavailable`). Les deux premières rejoignent `PUBLIC_ROUTES` ; le `/reset-password` natif reste hors liste blanche.
- **Aucune migration** : un lien de réinitialisation est une ligne de la table `verification` de Better Auth (déjà migrée, `GRANT` complets), identifiant `password-reset:<SHA-256 du jeton>`, valeur = l'adresse. Le jeton n'existe que dans l'e-mail, dans le fragment (`/reset-password#<jeton>`), comme le lien de vérification. **Ticket 10** : même table, avec son propre préfixe.
- **Mot de passe oublié** (`auth/passwords.ts`, `requestReset`) : une adresse sans compte reçoit aussi sa ligne, jamais cliquable (même idée que `pending_signup`) ; seul un compte ajoute la lecture de sa langue et l'envoi. Un lien par minute et par adresse, sous verrou consultatif (des demandes envoyées ensemble n'envoient qu'un e-mail, test) ; un nouveau lien remplace le précédent.
- **Fin de réinitialisation** (`completeReset`) : lien valide → **point d'insertion du code 2FA** (le compte est connu à cet endroit, rien n'est encore consommé) → HIBP (un refus laisse le lien intact) → dans une transaction : le lien est supprimé (deux requêtes ensemble : une seule passe, test), mot de passe écrit, **toutes** les sessions supprimées → `loginAttempts.succeeded` lève le blocage → e-mail `password_changed` → la route ouvre la session de l'appareil et l'enregistre dans `known_device`. **Ticket 11** : ajouter `code` au corps, un refus `two_factor_required` / code faux, et de quoi dire à l'écran qu'un code est attendu.
- **Écart à trancher** : après une réinitialisation, l'appareil est retenu **sans** e-mail `new_device` (`devices.signedIn(c, user, { announce: false })`) : l'Utilisateur reçoit déjà `password_changed`, et réinitialiser depuis un navigateur neuf est le cas courant. La revue note que la spec stack §7 prévoit l'e-mail à toute connexion sans cookie connu, et que `password_changed` ne nomme pas l'appareil.
- **Réauthentification** (`auth/reauthentication.ts`, réutilisable par 10 et 11) : `reauthenticate(userId, password)` renvoie `undefined`, `'wrong_password'` ou `'too_many_attempts'` ; `REAUTHENTICATION_STATUS` donne 403 et 429 (jamais 401, sinon la SPA déconnecte l'appareil) ; le schéma `currentPassword` est le champ `password` de toute requête sensible. Vérifié à chaque requête, sans fenêtre (test). **Ajout** : les mots de passe faux passent par les compteurs de `login_attempt` de l'adresse (ralentissement puis blocage de 15 min), pour qu'une session volée ne devine pas le mot de passe à loisir ; contrepartie relevée par la revue : dix connexions ratées par un tiers bloquent aussi les actions sensibles pendant 15 min.
- **Changer le mot de passe** (`change`) : réauthentification, HIBP, mot de passe écrit et autres sessions supprimées dans une transaction, e-mail `password_changed`. Un lien de réinitialisation déjà parti ne vaut plus rien (test).
- **HIBP** : `newPasswordRefusal(hibp, logger, password)` (`auth/hibp.ts`) sert à l'inscription, à la réinitialisation et au changement. Toujours pas de plugin `haveIBeenPwned` (écart du ticket 06).
- **E-mails** `password_reset_link` et `password_changed`, dans la langue de l'Utilisateur ; « Ce n'était pas moi » mène à `/forgot-password`. La langue est lue avant d'écrire le mot de passe : une fois écrit, plus rien ne peut faire échouer la réponse.
- **Purge** : la tâche `purge expired sessions and counters` efface aussi les liens de réinitialisation expirés (les nôtres seulement, par préfixe).
- **SPA** : `/forgot-password` (phrase neutre de la spec après l'envoi ; ouverte aussi avec une session, puisque « Ce n'était pas moi » y mène), `/reset-password` (nouveau mot de passe ; lien invalide ou sans jeton : « Ce lien n'est plus valable » et « Demander un nouveau lien » ; la réussite efface les données de l'appareil et mène à « Aujourd'hui »), lien « Mot de passe oublié ? » sur la connexion, et « Mot de passe » dans Réglages › Compte (mot de passe actuel, nouveau, message neutre « Mot de passe changé. Tes autres appareils sont déconnectés. », la liste des appareils est relue). `EmailField` et `PasswordField` factorisés (note du ticket 07), utilisés par la connexion et l'inscription.
- **Libellés à valider** : « Mot de passe oublié », « Envoyer le lien », « Retour à la connexion », « Nouveau mot de passe », « Changer le mot de passe », « Demander un nouveau lien », « Mot de passe actuel », « Mot de passe incorrect. », « Trop de tentatives. Réessaie dans 15 minutes. », et les textes des deux e-mails.
- **Revue (deux axes), corrigé** : le compte est lu avant le point d'insertion 2FA ; verrou sur le renvoi ; un changement de mot de passe annule les liens en cours ; langue lue avant le commit ; purge limitée à nos lignes ; écriture du mot de passe factorisée (`setPassword`).
- **Revue, relevé et laissé** : le message de blocage de la connexion reste un texte, le lien « Mot de passe oublié ? » est juste dessous ; le lien n'est vérifié qu'à l'envoi du nouveau mot de passe (pas de route de contrôle à l'ouverture) ; pas de limite par IP sur les deux routes de réinitialisation (une ligne et un e-mail par minute et par adresse, filet Traefik) ; une adresse avec compte fait deux lectures de plus qu'une adresse sans (écart de durée non mesuré) ; une connexion qui vérifie l'ancien mot de passe à l'instant du commit peut garder sa session ; le bouton « Afficher » ne fait 44 px sur mobile que dans Réglages ; quelques répétitions côté SPA (`edit`, écran de lien invalide) et dans les tests ; pas de parcours e2e (même raison qu'aux tickets 07 et 08).
